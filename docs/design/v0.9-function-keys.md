# v0.9.0 design: function keys

Status: **GREEN.** `decode_key` maps crossterm `F(1..=12)` to `KeyCode::F(n)` on both decode
paths, and the C poll skips F-keys with the skip-and-continue loop described below. The pinning
tests (named `red_*` from the RED slice) are `red_*` in `src/input.rs` (`function_key_tests`) and `src/tty_source.rs`
(`tests::function_keys`); guards that pass today are `guard_*` in the same modules.

Why: a consumer app wants F1 to open in-app help. `KeyCode` has no function-key variant, so the
key never reaches the application.

## 1. The public type

```rust
pub enum KeyCode { /* ... */ F(u8) }
```

`F(n)` is a function-key number (`F(1)` is F1), not a byte or a code point. v0.9 decodes F1
through F12. `KeyCode` is `#[non_exhaustive]`, so adding a variant is additive and non-breaking
for downstream `match`es, which already need a `_` arm. Inside the crate the exhaustive matches
are the places to check; there is one (the C poll, section 4).

F13+ is **open**, tracked in a follow-up issue. Not pinned by any test: crossterm and the kitty protocol also
report F13 through F35 (kitty `CSI 57376u`..`CSI 57398u`; xterm `CSI 25~`, `CSI 26~`, `CSI 28~`,
`CSI 29~`, `CSI 31~`..`CSI 34~`). The doc says F1..=F12 are decoded; whether F13+ is delivered or
dropped is not decided here.

## 2. Encodings

xterm modifier parameter = 1 + bitmask (shift 1, alt 2, ctrl 4).

| Key | SS3 | CSI tilde | With modifiers |
|-----|-----|-----------|----------------|
| F1  | `ESC O P` (VTE 0.76 sends this) | `CSI 11~` | `CSI 1;<mod>P` |
| F2  | `ESC O Q` | `CSI 12~` | `CSI 1;<mod>Q` |
| F3  | `ESC O R` | `CSI 13~` | `CSI 1;<mod>R` |
| F4  | `ESC O S` | `CSI 14~` | `CSI 1;<mod>S` |
| F5  |  | `CSI 15~` | `CSI 15;<mod>~` |
| F6  |  | `CSI 17~` | `CSI 17;<mod>~` |
| F7  |  | `CSI 18~` | `CSI 18;<mod>~` |
| F8  |  | `CSI 19~` | `CSI 19;<mod>~` |
| F9  |  | `CSI 20~` | `CSI 20;<mod>~` |
| F10 |  | `CSI 21~` | `CSI 21;<mod>~` |
| F11 |  | `CSI 23~` | `CSI 23;<mod>~` |
| F12 |  | `CSI 24~` | `CSI 24;<mod>~` |

- The gaps at 16 and 22 are real: `CSI 16~` and `CSI 22~` are not F-keys and stay dropped.
- `CSI P`, `CSI Q` and `CSI S` (no parameters) are F1, F2 and F4: the kitty protocol omits the
  `1` when no modifier is down. F3 has no such form because `CSI R` is the cursor position reply.
- Examples pinned: `CSI 1;2P` is Shift+F1, `CSI 1;5S` is Ctrl+F4, `CSI 15;3~` is Alt+F5.
- Fixture: `VTE_076_F1 = b"\x1bOP"`, the exact bytes VTE 0.76 sends for F1, must give
  `Key(F(1))` with no modifiers.

## 3. The two decode paths, and where F-keys are lost

Both paths converge on one function, so there is one place to fix.

1. **crossterm path** (`poll_event` when the source is crossterm, and every event that is not
   read by the owned source). crossterm 0.29 already produces `KeyCode::F(n)`. `decode_key`
   (`src/input.rs`) maps crossterm's key code and has `_ => return None`: **F-keys are lost
   there.**
2. **Owned Unix tty source** (`src/tty_source.rs`, bytes parsed by `src/tty_source/parse.rs`).
   `parse.rs` is crossterm 0.29's own decoder, and it already recognises every form in section 2:
   SS3 `P`..`S` (`parse_event`), the bare `CSI P/Q/S` (`parse_csi`), the modified
   `CSI 1;<mod>P`..`S` (`parse_csi_modifier_key_code`), and `CSI <n>;<mod>~`
   (`parse_csi_special_key_code`). It also handles the kitty event-type suffix (`:2` repeat, `:3`
   release) on those forms. The parser's result is crossterm's `Event::Key` with `KeyCode::F(n)`,
   queued as `SourceEvent::Terminal`, then handed through `decode_source_event`,
   `decode_source_event_as` and `decode_event_as` to the same `decode_key`: **F-keys are lost in
   `decode_key` again, not in the parser.** `src/tty_source.rs` already tests that the parser
   yields `F(5)` and its release (`kitty_272_repeats_and_releases_of_special_keys_keep_the_press_name`).

So the fix is a `CtKeyCode::F(n)` arm in `decode_key`; the parser needs no change. The byte-level
tests exist to pin the whole route (bytes to public `Event`) and to guard it.

Kitty keyboard-protocol reports: kitty sends F1 to F12 in these same legacy forms (with the
event-type suffix when flags ask for it), so the same arm covers them and the tests cover repeat
and release (`red_kitty_f_key_repeat_is_a_press_and_release_is_a_key_release`). Kitty reports
F13+ as `CSI <57376..57398>u`, which the parser also decodes to `F(13)`..; that is the open
question in section 1 (tracked in a follow-up issue).

A key release follows the existing rule (#275, #285): delivered as `Event::KeyRelease` only while
key-release reporting is on, never otherwise.

## 4. C ABI position

**Unchanged, and F-keys are skipped.** ABI v1 has no function-key constant (`GIBSON_KEY_*` is
`0x1001`..`0x100D`), and this work adds none: no constant, signature or struct changes. The
header comment in `include/gibson.h` says "F-keys are not exposed in ABI 1; they are skipped."

Ruling (GOD ruling, ACK RESULT #124): the **keep-polling** form. An F-key arriving on the C poll
(`gibson_poll_event`, `gibson_poll_event_kind`) is consumed and not reported, and the poll goes on
for the rest of its timeout. `GIBSON_EVENT_NONE` comes back only when the timeout expires (on a
headless context, which never waits, when the queue has nothing else). So C behaviour is exactly
what it is today, when `decode_key` drops F-keys before the C poll sees them; the only change is
that the skip now happens in `poll_event_impl` (`src/ffi.rs`) instead of in `decode_key`.

`poll_event_impl` loops: an F-key press or release is consumed and the poll continues with the
time left of the original deadline (as `poll_until_deliverable` does); a headless poll never waits.
Past the deadline on a terminal, at most `MAX_DROPS_PAST_DEADLINE` further F-keys are consumed
before the poll returns `GIBSON_EVENT_NONE`. (The RED commit had a stub that ended the poll at the
F-key.) The inner
`KeyCode::F(_) => 0` arm exists only to keep the match exhaustive and is unreachable once the loop
lands. `gibson_push_event` is untouched: it cannot express an F-key.

Tests, and why they are split this way:

- `src/ffi.rs` `function_key_tests` queue the Rust `Event` into a headless context's injected
  queue (`gibson_push_event` cannot express an F-key). A headless poll never waits, so these
  cannot test timing.
  - RED (a): `red_c_poll_skips_an_f_key_and_delivers_the_next_event`. F-key (press and release)
    then `a`: the poll must return the `a` key. The stub returns NONE.
  - GUARD (b, headless half): `guard_c_poll_of_a_lone_f_key_is_none_and_a_headless_poll_does_not_wait`.
    An F-key alone is NONE, and a headless poll still returns without waiting out its timeout
    (the header says a headless poll delivers "without waiting"; the GREEN loop must not sleep on
    an empty queue).
  - GUARD (c): `guard_c_poll_of_an_f_key_then_a_tick_is_what_a_tick_alone_is`.
- `tests/key_release_kind_pty.rs` `c_poll_skips_a_function_key_and_keeps_polling_to_its_deadline`
  is the real timing test for (b): over a real pseudo-terminal, a `gibson_poll_event(800 ms)` that
  sees only F-keys returns NONE only after the timeout (at least 700 ms), and an F-key then `b`
  in one write polls `b` at once. GUARD today (F-keys are still dropped upstream, and the poll
  keeps going); it turns red if F-keys are decoded and the C poll reports NONE at the first one,
  which is the regression it exists to catch.

## 5. SPEC UPDATE (GOD #148)

`// SPEC UPDATE (GOD #148): F-keys are modelled; was None`. Tests that used F5 as "an event no
platform delivers" now expect it, and keep what they guarded with Insert:

- `src/input.rs` `key_kind_tests::undelivered()`: F5 to Insert (the drop-and-keep-polling tests
  use it).
- `press_and_repeat_are_presses_and_a_release_is_not_delivered`: the `F(5)` press decodes to
  `F(5)` (RED); the unmodelled event is still `None`.
- `with_key_release_reporting_a_release_is_a_key_release_event`: the F5 release was `None`; with
  reporting on it is now `Event::KeyRelease(F(5))` (RED), `None` with reporting off. The
  unmodelled-key release guard now uses Insert.
- `tests/key_release_kind_pty.rs`: the bytes `CSI 15~` become `CSI 2~` (Insert), so the
  "dropped release does not end the poll" guard still has a dropped key to send.

## 6. Guards (pass today, must stay green)

- Unknown or unsupported sequences (`CSI 99~`, `ESC O Z`, `CSI 16~`, `CSI 22~`) produce no event.
- F-key bytes, and a delivered F-key event, put no character into a `TextInputState`, and the
  editor does not claim the event.
- Arrow, Home, End, Delete, PageUp and modified forms decode as before (`CSI A`, `ESC O A`,
  `CSI H`, `CSI 1;5C`, and others).
- A key that stays unmodelled (crossterm `Insert`, `Null`, `CapsLock`, `Media(..)`) decodes to
  `None`.
