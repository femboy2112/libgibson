# v0.9.0 toast lane (design, RED slice)

Status: **EXPERIMENTAL design, RED slice only.** `toast_lane` exists as a deliberately wrong stub and
`tests/toast_lane.rs` pins the intended behavior; the `red_` tests fail by assertion until the GREEN
slice lands. The slice was prepared without compiling (a shared build lock); CI is the first compile.
Nothing here changes `toast()`.

## 1. Problem

`toast(text)` lowers (`src/ui/compile.rs`, `ElementKind::Toast`) to a panel inside a 100% x 100%
column aligned End/End, so it always lands at the bottom-right of the box it is mounted on. Overlays
mount as absolute children of the host element's wrapper (`docs/UI_LAYER.md`), so:

- two toasts in one host overlap each other;
- a consumer that wants toasts stacked top-right under a header, never over a side rail, hand-builds
  a column of per-toast fixed-height boxes with copied geometry.

## 2. API

```rust
// ui/element.rs; reaches ui and ui::prelude through `element::*`. No new module.
pub fn toast_lane<A>(toasts: impl IntoIterator<Item = Element<A>>) -> Element<A>;
```

A noninteractive overlay host, mounted with `.overlay(...)` on the element whose rect the toasts
must stay inside (for example the transcript column):

```rust
let transcript = column().grow(1.0).child(/* ... */).overlay(toast_lane(newest_first));
row().child(transcript).child(rail)   // header and rail are outside the host, so never covered
```

## 3. Semantics

- **Order and anchor.** Toasts stack from the host's top-right corner in the given order. The caller
  passes the newest first; the first toast is topmost.
- **Boxes.** Each toast gets its own box of the toast's height: 3 rows by default, or its
  `.height(...)`. Boxes are consecutive and disjoint, so toasts never overlap.
- **Width.** `min(toast width, host width)`, right-aligned. The toast width is its `.width(...)`,
  default 36, exactly as for a plain toast.
- **Capacity.** `k = floor(host_h / toast_h)`.
- **Overflow is never silent.** With `n` toasts and `n > k`, the `k - 1` newest are drawn and the
  last box becomes a "+N more" row with `N = n - (k - 1)`; the oldest toasts collapse into it. With
  `k = 6` and `9` toasts: 5 drawn plus "+4 more". With `n <= k`, all are drawn and there is no
  "+N more" row.
- **Too small.** A host shorter than one toast (`k = 0`) draws nothing, not even "+N more".
- **Inert.** The lane is never a hit or focus target, and it paints nothing outside the host.
- **Unchanged.** A plain `.overlay(toast(...))` still lands bottom-right.

## 4. GREEN sketch (not implemented)

Composition covers most of it: each toast lowered inside a full-width box of its own height already
ends up right-aligned in that box, because the plain toast wrapper aligns End/End inside a box of the
toast's own height. A new `ElementKind::ToastLane` would lower to a 100% x 100% column of those
boxes. The capacity rule needs the host's resolved height, which compile (before layout) does not
have. Candidate seams: a layout-time node that decides how many boxes to draw from its resolved
height; or a second compile pass fed the host height. Plain clipping alone is not enough, because it
would draw a cut-off toast instead of "+N more". This is open question 5.1.

## 5. Open questions

1. **Capacity at compile time.** Which seam produces `k` (see section 4)? The RED tests only pin the
   result.
2. **k = 1.** The proposal (and the RED test `red_capacity_one_shows_only_the_more_row`) is that the
   only box is "+N more" with `N = n`, so no toast text is visible. The alternative is to show the
   newest toast and drop the overflow row for `k = 1`, which would drop toasts silently, so it is
   rejected for now.
3. **Mixed heights.** Is `k` computed from the first toast's height, or are boxes consumed
   sequentially until the host runs out? And what height does the "+N more" row take (the default 3,
   or the height of the box it replaces)? The RED tests use uniform default-height toasts.
4. **"+N more" row.** Its tone, its wording for other locales, and whether it is a plain toast
   (inherits chrome and motion) or a lane-owned element. The tests pin only the text "+N more".
5. **Motion.** Do toasts that shift up as older ones expire animate? Toast motion is keyed per
   element today.
6. **Interaction.** A toast carrying `on_press`/`on_dismiss` inside a lane: the lane itself is inert,
   but does each toast stay a target? Proposed: yes, the lane forwards nothing and adds no target.
7. **Anchor.** Top-right only. A `Corner` option (bottom-right with stacking upward) is deferred;
   it would be an additive builder method.

## 6. Tests (`tests/toast_lane.rs`)

| Test | Kind | Pins |
| --- | --- | --- |
| `guard_plain_overlay_toast_stays_bottom_right` | guard | ordinary `toast()` unchanged |
| `guard_empty_lane_draws_nothing` | guard | an empty lane paints nothing |
| `red_header_and_rail_are_never_covered_by_the_lane` | red | every cell outside the host is identical to the no-toast frame, at widths 80 and 100 |
| `red_toasts_occupy_disjoint_boxes_stacked_from_the_top_right` | red | box `i` holds toast `i`, flush right, top first, no overflow row |
| `red_overflow_collapses_the_oldest_into_a_plus_n_more_row` | red | k = 3, 6 toasts: 2 drawn plus "+4 more" |
| `red_capacity_one_shows_only_the_more_row` | red | k = 1: only "+N more" (open question 2) |
| `red_host_shorter_than_one_toast_draws_nothing` | red | 2-row host: frame identical to no-toast; 4-row host draws one toast |

The stub returns a 100% column holding the toasts, so the first toast lands bottom-right and the rest
fall outside the host: every red test fails on an assertion about position or presence.
