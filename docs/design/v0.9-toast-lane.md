# v0.9.0 toast lane (design, RED slice)

Status: **EXPERIMENTAL design, RED slice only.** `toast_lane` exists as a deliberately wrong stub and
`tests/toast_lane.rs` pins the intended behavior; the `red_` tests fail by assertion until the GREEN
slice lands. The slice was prepared without compiling (a shared build lock); CI is the first compile.
Nothing here changes `toast()`.

## 1. Problem

`toast(text)` lowers (`src/ui/compile.rs`, `ElementKind::Toast`) to a panel inside a 100% x 100%
column aligned End/End, so it always lands at the bottom-right of the box it is mounted on. Overlays
mount as absolute children of the host element's wrapper (`docs/UI_LAYER.md`), so:

- two toasts in one host overlap each other;
- a consumer that wants toasts stacked top-right under a header, never over a side rail, hand-builds
  a column of per-toast fixed-height boxes with copied geometry.

## 2. API

```rust
// ui/element.rs; reaches ui and ui::prelude through `element::*`. No new module.
pub fn toast_lane<A>(toasts: impl IntoIterator<Item = Element<A>>) -> Element<A>;
```

A noninteractive overlay host, mounted with `.overlay(...)` on the element whose rect the toasts
must stay inside (for example the transcript column):

```rust
let transcript = column().grow(1.0).child(/* ... */).overlay(toast_lane(newest_first));
row().child(transcript).child(rail)   // header and rail are outside the host, so never covered
```

## 3. Semantics

- **Order and anchor.** Toasts stack from the host's top-right corner in the given order. The caller
  passes the newest first; the first toast is topmost.
- **Boxes.** Each toast is drawn at its own height: 3 rows by default, or its `.height(...)`. Boxes
  are consecutive and disjoint, so toasts never overlap. Heights may be mixed.
- **Width.** `min(toast width, host width)`, right-aligned. The toast width is its `.width(...)`,
  default 36, exactly as for a plain toast.
- **Fill rule.** With host height `H`, newest toast height `h0` and `n` toasts, in order:
  1. If the heights of all `n` toasts sum to at most `H`, draw them all. There is no counter.
  2. Else if `H < h0` (the host is shorter than the newest toast), draw nothing.
  3. Else if `H < h0 + 1` (the newest fits but the newest plus a counter row does not; `n > 1`
     here), draw the newest toast and put a right-aligned " +N" on its top row, with `N = n - 1`
     hidden toasts. A lone counter that hides all content is never drawn.
  4. Else reserve one row for the counter: walk the toasts newest first, placing each at its actual
     height, and stop at the first toast that would not fit in (remaining height - 1). Then draw a
     one-row "+N more" directly below the last drawn toast, with `N` = the number of hidden toasts.
- **The counter row is one row high, always.** It is plain text styled like a toast, right-aligned
  like one, and is not itself a toast box.
- **Worked examples.**
  - Uniform: `H = 9`, six 3-row toasts. The newest fits in 8, the second in 5, the third does not
    fit in 2. Two toasts plus "+4 more" (rows 0..3, 3..6, then the counter at row 6).
  - Capacity one: `H = 3`, three 3-row toasts. Rule 3: the newest toast, with " +2" at the right
    end of its top row.
  - Mixed: `H = 8`, newest first with heights 2, 4, 3. The total 9 exceeds 8. 2 fits in 7 (leaving
    6), 4 fits in 5 (leaving 2), 3 does not fit in 1. Two toasts plus "+1 more" at row 6; row 7 is
    empty.
- **Inert.** The lane is never a hit or focus target, and it paints nothing outside the host.
- **No motion.** The lane adds no motion in v0.9: toasts appear and disappear instantly, which is
  reduced-motion-safe, and toasts do not slide when older ones go away.
- **Unchanged.** A plain `.overlay(toast(...))` still lands bottom-right.

## 4. GREEN sketch (not implemented)

Composition covers most of it: a toast lowered inside a full-width box of its own height already
ends up right-aligned in that box, because the plain toast wrapper aligns End/End. A new
`ElementKind::ToastLane` would lower to a 100% x 100% column of those boxes plus the counter. The
fill rule needs the host's resolved height, which compile (before layout) does not have.
Plain clipping is not enough, because it would draw a cut-off toast instead of a counter.

## 5. Decisions and open questions

Decided (release owner):

1. **Overflow counter.** One row high, always; capacity one uses the inline " +N" (rule 3), never a
   lone "+N more".
2. **Mixed heights.** Walked newest first at their actual heights (rule 4); no per-lane `k`.
3. **Capacity seam.** GREEN picks the smaller of {a layout-time node, paint-time capacity} and
   reports which one it chose.
4. **Motion.** None in v0.9 (section 3).

Still open:

1. **Counter styling and wording.** Tone, and wording for other locales. The tests pin only the
   text "+N more" and " +N".
2. **Interaction.** A toast carrying `on_press` or `on_dismiss` inside a lane: the lane itself is
   inert, but does each drawn toast stay a target? Proposed: yes, and the lane adds no target.
3. **Hidden toasts.** Whether a hidden toast's `on_dismiss` is reachable (it is not, as proposed);
   the application owns expiry.
4. **Anchor.** Top-right only. A bottom-right, stack-upward option is deferred and would be an
   additive builder method.
5. **Counter placement.** Directly below the last drawn toast (as tested), not pinned to the
   host's bottom edge.

## 6. Tests (`tests/toast_lane.rs`)

| Test | Kind | Pins |
| --- | --- | --- |
| `guard_plain_overlay_toast_stays_bottom_right` | guard | ordinary `toast()` unchanged |
| `guard_empty_lane_draws_nothing` | guard | an empty lane paints nothing |
| `red_header_and_rail_are_never_covered_by_the_lane` | red | every cell outside the host is identical to the no-toast frame, at widths 80 and 100 |
| `red_toasts_occupy_disjoint_boxes_stacked_from_the_top_right` | red | box `i` holds toast `i`, flush right, top first, no counter when all fit |
| `red_overflow_collapses_the_oldest_into_a_plus_n_more_row` | red | `H = 9`, six toasts: 2 drawn plus a one-row "+4 more" |
| `red_capacity_one_shows_the_newest_with_an_inline_count` | red | `H = 3`, three toasts: the newest plus " +2" right-aligned on the top row |
| `red_mixed_heights_fill_by_actual_height_with_a_one_row_counter` | red | `H = 8`, heights 2, 4, 3: two toasts plus "+1 more" at row 6 |
| `red_host_shorter_than_one_toast_draws_nothing` | red | 2-row host: frame identical to no-toast; 4-row host draws one toast |

The stub returns a 100% column holding the toasts, so the first toast lands bottom-right and the rest
fall outside the host: each red test fails on an assertion about position or presence. The
capacity-one test is the one whose first assertions pass under the stub (the newest toast already
fills a 3-row host); it fails on the missing " +2".
