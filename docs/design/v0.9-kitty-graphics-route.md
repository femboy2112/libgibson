# v0.9 kitty graphics pixel route (design, RED slice)

Status: **design plus RED slice.** `src/graphics/kitty.rs` holds API stubs that compile and do
nothing; `tests/kitty_graphics.rs` pins the behaviour GREEN must deliver. Nothing here touches the
renderer, nothing is enabled by default, and nothing was compiled by the author (a shared build
lock): hosted CI is the first compile. Every test runs on bytes and `Surface`s; no escape sequence
is written to a terminal and every image is a formula-generated synthetic sprite.

This document turns the route sketched in [KITTY_IMAGES_DESIGN.md](../KITTY_IMAGES_DESIGN.md)
(merged #365) into a concrete API and test plan, and it replaces that document's "†" list with a
verified/unverified ledger (section 1).

> Glyph encoders raise edge detail, not chroma; concept-art fidelity needs pixels.

(Owner note, quoted verbatim.) Every cell encoder draws one-column glyphs with two colours per
cell, so a denser grid sharpens edges and luminance but cannot add colours inside a cell. Painted
art needs the pixels themselves. This route is the one that carries them.

## 0. Scope in one paragraph

An application opts in. LibGibson transmits an RGBA image once (APC, chunked base64), creates a
*virtual placement* of `cols x rows` cells, and fills the image's box with ordinary text cells:
U+10EEEE plus a row and a column diacritic, foreground colour = image id. Those cells are
`Cell`s in a `Surface`, so the existing diff, clip, compositor and renderer already move, hide and
restore the picture. Where the route is unavailable, the same box is drawn by the cell encoder the
application chose (`CellEncoder`, merged in #436).

## 1. Verification ledger (kitty graphics protocol page)

Source: the protocol page <https://sw.kovidgoyal.net/kitty/graphics-protocol/> and its linked
`rowcolumn-diacritics.txt`, fetched as raw HTML/text on 2026-11-19. "Verified" means the page text
says it. Nothing was checked against a running kitty (no terminal was touched); that is gate 2 of
section 12.

### Verified from the page

- **transmit**: `ESC_G<keys>;<base64>ESC\`; `a=t` transmit, `a=T` transmit and display, `a=p` place,
  `a=q` query, `a=d` delete
- **raw pixels**: `f=32` RGBA (default), `f=24` RGB, `f=100` PNG; for raw data `s=` width and `v=`
  height are required
- **id**: `i=` is 1..4294967295, never 0
- **medium**: `t=d` direct (default), `f` file, `t` temp file, `s` shared memory; a remote client
  must use direct
- **chunking**: base64 first, then chunks of at most 4096 bytes; every chunk but the last a multiple
  of 4; `m=1` on all but the last, `m=0` on the last; only the first chunk carries the full keys,
  later chunks only `m` and optionally `q`; all chunks of one image must finish before any other
  graphics command; nothing displays until the sequence is complete
- **compression**: `o=z` is zlib (RFC 1950), applied before base64 (optional; not used in this
  slice)
- **quiet**: `q=1` suppresses OK replies, `q=2` suppresses failure replies; the placeholder section
  says to create the image "in quiet mode (q=2) so that there are no responses"
- **virtual placement**: `a=p,U=1,i=<id>,c=<cols>,r=<rows>`; can be combined with `a=T`; the image
  is fit to the rectangle with aspect ratio preserved; a missing or short placeholder box shows only
  part of the image
- **placeholder**: `U+10EEEE`; "image ID in its foreground color"; only the fg is used for the id,
  so ids are 8-bit in 256-colour mode or 24-bit in true-colour mode; a third diacritic carries the
  most significant byte (example: id 33554474 = 42 + (2 << 24), third diacritic U+030E)
- **underline colour**: carries the placement id; omitted or zero means the terminal may pick any
  virtual placement of the image
- **background**: the cell background is visible where the image is transparent
- **diacritics**: row and column are `rowcolumn-diacritics.txt`: 297 entries, entry 0 = U+0305, 1 =
  U+030D, 2 = U+030E, 3 = U+0310, 4 = U+0312, 5 = U+033D, 6 = U+033E, 7 = U+033F, 8 = U+0346, 9 =
  U+034A, ... last (296) = U+1D244. All 297 entries are combining class 230
- **omitted diacritics**: the terminal infers them from the cell to the left under three rules; they
  fail for horizontal scrolling and overlapping images. We always write both
- **ids are global**: the page says ids live in a global namespace and can collide
- **delete syntax**: `a=d,d=<x>`: `i`/`I` by image id (with `p=` for a placement), `n`/`N` by
  number, `a`/`A` all visible placements, `r`/`R` id range `x..=y` (kitty 0.33.0), plus cell,
  column, row, z-index and frame variants
- **lower vs upper**: lowercase deletes placements without freeing data; uppercase also frees the
  data if the image is not referenced elsewhere, "such as in the scrollback buffer"
- **virtual placements**: can be deleted only with `d` = `i`, `I`, `r`, `R`, `n` or `N`; the keys `a
  c p q x y z` and their capitals "never affect virtual placements"
- **delete vs upload**: a delete received during a chunked upload aborts the partial upload
- **placeholder images**: are "not considered placements from the protocol perspective"; they are
  moved, deleted or modified by manipulating the underlying placeholder text
- **reset and clear**: terminal reset clears visible images; switching to the alternate screen
  (1049) clears the alternate screen's images; `ESC[2J` clears all images; the other erase commands
  have no effect on graphics; scrolling moves images with the text
- **support probe**: `e=T` with `U=1` in a feature query; placeholders added in kitty 0.28.0
- **hosts**: the page names tmux, vim and weechat as hosts that can carry placeholders, if they can
  pass escape codes through
- **quota**: terminals "should" have a storage quota and delete older images when it is exceeded
  (kitty: 320 MB per buffer); images without placements go first

### Not on the page (still unverified)

1. Which terminals other than kitty implement placeholders. The page does not list any.
2. How the 24-bit fg maps to the id. The page implies "24-bit IDs"; the byte order (`r<<16 | g<<8
   | b`, with the low byte equal to the 8-bit value) is **assumed** from the id-42 examples.
3. Whether `q=2` suppresses OK replies too. Read alone the reference text says it suppresses
   failure replies only; the placeholder section calls `q=2` "no responses". A real-terminal PTY
   test that reads stdin during an upload must settle it (an OK reply would land in the
   application's input stream).
4. Whether RGBA is straight or premultiplied alpha. `RgbaRaster` is straight; the page is silent.
5. What a placeholder cell shows when its image id is unknown or was evicted (blank vs a tofu
   box), and what a second `a=p,U=1` for the same id does (replace or add). This design avoids
   the question: it deletes the placements by id before re-creating one (section 7).
6. Whether images are per screen buffer (main vs alternate). The page only says the alternate
   screen's images are cleared on entry. This design assumes they are and resets the cache on
   every screen switch (section 8).
7. Whether `d=I` frees the data of an image that only had a virtual placement; the page says
   "provided the image is not referenced elsewhere".
8. tmux/screen passthrough framing (`ESC Ptmux;...`, doubled ESC, `allow-passthrough`): not on the
   page. Not implemented; the route is off by default there (section 10).
9. The cell pixel size (needed to choose `cols x rows` for a given aspect ratio): the page does not
   cover it; `TIOCGWINSZ` pixel fields or `CSI 16 t` are outside this slice.

The tests encode only verified facts, plus assumption 2 (the packed id) and assumption 3 (`q=2`)
as explicitly labelled choices.

## 2. Command bytes

All three commands are pure functions returning `Vec<u8>`; the application (or the renderer, in
section 12's GREEN step) writes them. Keys are chosen from the verified table above.

- **transmit**: `ESC_Ga=t,f=32,s=<w>,v=<h>,i=<id>,q=2;<base64>ESC\`; why these keys: `a=t` transmits
  without displaying (the placeholder route wants no real placement); `f=32` RGBA; `s`,`v` mandatory
  for raw pixels; `i` the content id; `q=2` no replies. `t=d` is the default and is omitted
- **transmit, chunked**: first `...,q=2,m=1;<first 4096 base64 chars>`, then
  `ESC_Gq=2,m=1;<chunk>ESC\` ..., last
  `ESC_Gq=2,m=0;<chunk>ESC\`; why these keys: verified chunk rules; `q=2` repeated on later chunks,
  which the page allows ("`m` and optionally `q`")
- **place**: `ESC_Ga=p,U=1,i=<id>,c=<cols>,r=<rows>,q=2ESC\`; why these keys: virtual placement; no
  `C=1` because a virtual placement has no screen position and moves no cursor
- **delete, keep data**: `ESC_Ga=d,d=i,i=<id>,q=2ESC\`; why these keys: removes placements (and so
  the display); data stays for instant re-show
- **delete, free**: `ESC_Ga=d,d=I,i=<id>,q=2ESC\`; why these keys: also frees the data
- **delete all ours**: one free-delete per id, ascending, de-duplicated; why these keys: by id
  because `d=a`/`d=A` never affect virtual placements

A single-chunk upload omits `m`; a 2x2 RGBA image is exactly
`ESC_Ga=t,f=32,s=2,v=2,i=7,q=2;/wAA/wD/AP8AAP//////gA==ESC\` for the pixels
`FF0000FF 00FF00FF 0000FFFF FFFFFF80`. The split point is pinned at 4096 base64 characters
(32x24 RGBA, one chunk) and 4224 (33x24 RGBA, 4096 + 128).

`kitty_transmit_rgba` returns an empty `Vec` for input it must refuse (wrong buffer length, zero
size, id 0 or id above `0x00FF_FFFF`) so a bad call can never put a malformed APC on the wire.

## 3. Placeholder cells in `Surface`

A placeholder cell for `(row r, col c)` of image `id`:

- glyph: `U+10EEEE` + `rowcolumn_diacritic(r)` + `rowcolumn_diacritic(c)`, one grapheme,
  `display_width == 1`;
- style: `fg = Color::Rgb(id >> 16, id >> 8, id)`, `bg = None`, no attributes;
- `is_continuation = false`, `transparent = false`.

Both diacritics are always written. Inference from the left neighbour is unreliable under the
diff, which writes cells out of order and in isolated runs, and under clipping. Ids are limited to
`1..=0x00FF_FFFF` so the optional third (most significant byte) diacritic never appears.
`placeholder_cells(id, cols, rows)` clamps each dimension to 297, the size of the diacritic table.

The placement id (underline colour) is **not used**. `Style` has no underline colour and adding
a field to a public, literal-constructible struct would be a breaking change. One virtual
placement per image id is enough as long as one box shows an id at a time (section 7).

### Why occlusion, clipping and restore are free

The picture is not an overlay; it is what the terminal draws *for* those text cells. Therefore:

- **Occlusion.** A modal or toast paints its own cells over the placeholder cells in the `Surface`.
  Those frame cells now hold text, so the terminal draws text there and no image (the image follows
  the placeholder text, per the page). The cells outside the modal are still placeholders and keep
  showing their part of the image. No graphics command is involved.
- **Restore, no flash.** When the modal closes the next frame's diff differs from the occluded
  frame only at the covered cells, and `compute_diff` emits exactly those cells' glyphs again. The
  terminal redraws the image fragments from image data it already holds. No upload is sent, so
  there is nothing to flash. `tests/kitty_graphics.rs` pins this: exactly the covered placeholder
  cells reappear, byte-exact, and no `ESC_G` byte is written either way.
- **Clipping.** Row and column are absolute diacritics, so a sprite clipped by a viewport, the
  frame edge or a panel border keeps the right (row, col) on every surviving cell; the compositor
  never re-bases them. The page's "partial box shows part of the image" rule does the rest.
- **Idle frames.** An unchanged `Surface` gives an empty diff and the renderer emits 0 bytes
  (`acid_render` already asserts that for ordinary content; the new test repeats it with
  placeholder cells). The upload is a separate write that happens only when the id is new.

`CSI K` and other text erases over a placeholder cell remove the image from that cell exactly as
they remove text; they do not free image data. That is the behaviour the occlusion path relies on
and it is the thing the real-kitty PTY test (section 12, gate 2) must confirm.

### Does `Glyph::new` hold a placeholder?

`Glyph::new` measures with `UnicodeWidthStr::width(s).min(2)`. U+10EEEE is a Private Use
character (width 1 in `unicode-width`) and the diacritics are combining marks (width 0), so the
expected result is width 1 and, by grapheme segmentation, a single cluster. This was **not run**
(no cargo). `guard_glyph_new_keeps_placeholder_plus_diacritics_as_one_width_1_grapheme` asserts
it. If CI shows it RED, `cell.rs` needs one change: `Glyph::new` and `Glyph::from_char` must pin
the width of any string that starts with U+10EEEE to 1. No other change to `cell.rs` is expected.

## 4. Id cache

`ImageCache::ensure(&RgbaRaster) -> (id, Option<upload bytes>)`.

- Key: a deterministic 64-bit FNV-1a hash of `(width, height, pixels)`; width and height are in
  the key so the same bytes at two shapes are two images.
- Id: the hash folded to 24 bits, never 0, linear-probed to the next free value on collision with
  another image *in this cache*. A pure function of the pixels and the cache's own history: no
  clock, no randomness, no environment.
- The first `ensure` of a raster returns its id and the upload bytes; every later call returns the
  same id and `None`. A changed raster has a different hash, so a new id and a new upload.
- An image over `CacheLimits::max_upload_bytes` is refused: `(0, None)`. Id 0 means "not
  resident, use the fallback".
- Ids share the terminal's global namespace with every other program (and every other copy of
  LibGibson). Collisions with foreign images cannot be detected without a query. Open question 3.

## 5. Pose switching by id

An avatar with several poses uploads each pose once (each a distinct id) and switches by changing
the foreground colour of the box's placeholder cells from one id to another. The diff then rewrites
`cols x rows` cells (about 20 bytes each) and sends no image byte. Going A, B, A re-uploads nothing:
A's id is still resident and the third `ensure` returns it with `None`. A pose switch is
cell-sized; an animation that switches every frame is `cols x rows x ~20` bytes per frame.

Residency is capped (`max_resident_images`). Beyond the cap the least recently shown image is freed
with `kitty_delete(id, true)` and its next `ensure` uploads again.

## 6. Byte budgets

- **per-upload cap**: 4 MiB raw RGBA; behaviour: over the cap: `ensure` returns `(0, None)`, the box
  uses the fallback, the refusal is reported
- **per-frame budget**: 256 KiB of base64; behaviour: uploads beyond the budget are deferred; their
  boxes show the fallback until the upload has been *written*
- **resident images**: 16; behaviour: least recently shown freed beyond it

A raster is at most 2048 x 2048, so one image is at most 16 MiB raw / 22 MiB of base64; the
upload cap normally bites before that. `zlib` (`o=z`) is optional and deferred: it needs a
compressor (no new dependency in this slice), and flat synthetic art compresses well, so it is a
later measured step.

An image counts as resident only once its bytes were **written** to the writer successfully, the
same discipline as `last_emitted_depth` (advance after a successful commit). The renderer cannot
know the terminal accepted it: there is no reply channel (`q=2`), so "resident" means "emitted",
and a terminal that drops the upload (quota, an unsupported terminal) shows blank placeholders.
This is why the route is opt-in and gated (section 10) and why section 9's claim is limited.

The per-frame deferral needs a frame-plan type (`begin_frame`, deferred set); its tests are not in
this slice (open question 5).

## 7. Placement lifetime

One virtual placement per image id, created after the upload and before the first frame that uses
it. If the box size for an id changes (resize, relayout), the sequence is
`kitty_delete(id, false)`, then `kitty_place_virtual(id, new_cols, new_rows)`, then the frame. The
delete-then-place order avoids depending on what a second `a=p,U=1` does (unverified item 5).
Consequence: an id has one active box size. A second box showing the same image at a different
size takes the fallback path (or the application gives it a distinct raster).

All of a frame's graphics bytes (uploads, deletes, placements) go **before** the frame's cell bytes
inside the same `TerminalTransaction`, so they are inside one synchronized-update region
(`?2026h`..`?2026l`) when the terminal supports it. Whether a terminal presents APC atomically
inside that region is unverified.

## 8. Teardown and the panic hook

- **Normal teardown** (`Context::restore` and `Drop`): write `ImageCache::teardown_bytes()` (a
  free-delete for every transmitted id) before leaving the alternate screen, showing the cursor
  and resetting SGR. Fullscreen: the leave itself clears the alternate screen's images (verified)
  but the explicit delete frees the data too, and covers inline mode, which has no screen switch.
- **Panic hook.** The existing process-global hook cannot borrow the owning session. GREEN adds a
  process-global registry of resident ids (a `Mutex<BTreeSet<u32>>`, filled when an upload is
  written, emptied by teardown) and a public `delete_all_images()` that writes
  `kitty_delete_all(&ids)` to stdout. The hook calls it with `try_lock` only, on the owner thread
  only (the same rule as the existing cleanup), so a panic while the registry is locked cannot
  deadlock. An application can call it from its own panic or signal path. Order in the hook:
  delete, then the existing screen cleanup.
- **Torn writes.** After a failed or partial write the renderer's `physical_uncertain` recovery
  frame starts with the delete of every id it ever transmitted (a delete aborts a half-sent
  chunked upload: verified) and clears the cache, so the recovery repaint re-uploads. Nothing is
  assumed resident after an uncertain write.
- **Screen switches and resets.** The cache is forgotten (and re-uploaded on demand) whenever the
  session enters or leaves the alternate screen, and on any terminal reset or `ESC[2J` the
  renderer itself issues, because the page says these clear images.
- Signals that end the process without running Rust code (SIGKILL, OOM) can leave data pinned in
  the terminal's quota. That is the same best-effort boundary as the rest of the terminal lease
  (`docs/TERMINAL_LEASE_CONTRACT.md`); the placeholders are text and vanish with the screen.

## 9. The fallback contract: same box, cell encoder

An image element reserves `columns x rows` cells whatever it paints. Its three renderings share
one layout:

- **pixels**: `pixel_route` returns `Pixels` and the image is resident; cells: placeholder cells
- **cell encoder**: everything else with colour; cells: `to_surface_with(encoder)`; the default
  `HalfBlock` is byte-identical to today's `ui::image`
- **alt text**: `ColorDepth::Mono`; cells: the alt text, as today

Truthful fallback rules:

1. Never claim pixels it cannot show. A box uses placeholders only after the upload was written
   successfully; before that (deferred, refused, failed) it shows the encoder form.
2. The decision is recomputed per frame from `(capability, depth, environment, residency)`. A
   mid-session colour-depth drop below true colour turns pixel boxes into encoder boxes on the next
   frame, because quantizing the foreground would corrupt the id (the existing restyle repaint
   already handles a depth change).
3. The fallback is an explicit, reported outcome, never silent: the terminal adapter records which
   route each image box used in a per-frame route report, so an application can log "pixels
   unavailable, using sextant".
4. The claim stops at "bytes emitted". A terminal can drop an image silently; LibGibson does not
   probe (design doc: no default query), so it does not claim the pixels are on screen.
5. History is never pixel (section 11): a committed line is always the encoder form.

## 10. Multiplexer, remote and capability policy

`pixel_route(cap, depth, force, get_env) -> PixelRoute` is a pure function; the environment is read
only through `get_env`, only to switch the route **off**:

- **`cap` is `Unknown`**: `Fallback(NotOptedIn)`; never upgraded by `TERM`, `KITTY_WINDOW_ID`,
  `TERM_PROGRAM`; not even by `force`
- **`cap` is `Unsupported`**: `Fallback(Unsupported)`; not even by `force`
- **depth below `TrueColor`**: `Fallback(NotTrueColor)`; not even by `force`
- **`TMUX` or `STY` set, or `TERM` starting `screen` or `tmux`**: `Fallback(Multiplexer)` unless
  `force`
- **`SSH_CONNECTION`, `SSH_TTY` or `SSH_CLIENT` set**: `Fallback(Remote)` unless `force`
- **otherwise**: `Pixels`

`force` exists for an application that has configured tmux passthrough itself; LibGibson does not
frame APC for a multiplexer in this slice (unverified item 8).

## 11. Inline mode: scroll, resize, commit to history

The inline live region is redrawn in place by the cell diff; scrollback above it is terminal-owned.

- **Scroll.** Placeholder cells are text, so the terminal scrolls them with the text. When the live
  region grows and pushes rows into scrollback, those rows keep their placeholders and keep showing
  the image while the image data is resident (the page: images scroll along with text).
- **Resize.** A resize re-anchors the region (`AnchorState::Invalid`, `previous_surface = None`):
  the next frame repaints every cell including placeholders, with the same ids, so **no upload is
  re-sent**. If layout gives the box a new size the id's placement is re-created (section 7)
  before that frame. Rows the *terminal* pushed into scrollback during a shrink are out of reach
  (`ReanchorReport`'s existing limitation); here that means stale placeholder rows may sit in
  scrollback and show the old picture until the data is freed. That is cosmetic, bounded by the
  residency cap and by teardown, and the same class as stale text rows today.
- **Commit to history.** `commit_*` and `insert_*_before_live` turn a node into ANSI lines. **The
  delete-on-commit policy: committing never leaves a placeholder in history.** The commit path
  compiles image elements in their encoder form, so scrollback holds ordinary half-block (or
  chosen encoder) cells. Reasons: history is immutable and is reflowed by terminals on resize,
  which splits placeholder rows and columns; a quota eviction or the teardown delete would leave
  placeholder text that renders as nothing (or a missing-glyph box); and copy and paste of history
  must stay readable. Consequence: a commit frees nothing by itself. After the commit the live
  region is repainted (full repaint), the id is reused, and no image bytes are sent.
- **Freeing.** An id absent from the current frame is deleted without freeing (`d=i`) at the end of
  the frame, so it stops being displayed but stays instantly re-showable; its data is freed
  (`d=I`) when the residency cap evicts it or at teardown. This refines the design doc's "old one
  deleted once no placeholder cell refers to it": freeing is eviction-driven so that returning to
  an earlier pose costs nothing.
- **Clearing.** `Context::clear_live_region` erases cells (the images go with them) and leaves the
  data resident.

## 12. API

```rust
// src/graphics/kitty.rs; module `gibson::graphics::kitty`. All RED stubs.
pub const PLACEHOLDER: char = '\u{10EEEE}';
pub const MAX_CHUNK_BASE64: usize = 4096;
pub const MAX_IMAGE_ID: u32 = 0x00FF_FFFF;
pub const MAX_PLACEHOLDER_DIM: u16 = 297;

pub fn kitty_transmit_rgba(id: u32, w: u32, h: u32, rgba: &[u8]) -> Vec<u8>;
pub fn kitty_place_virtual(id: u32, cols: u16, rows: u16) -> Vec<u8>;
pub fn kitty_delete(id: u32, free: bool) -> Vec<u8>;
pub fn kitty_delete_all(ids: &[u32]) -> Vec<u8>;
pub fn rowcolumn_diacritic(n: u16) -> Option<char>;
pub fn placeholder_cells(id: u32, cols: u16, rows: u16) -> Surface;

#[non_exhaustive] pub struct CacheLimits { pub max_upload_bytes: usize,
    pub max_frame_bytes: usize, pub max_resident_images: usize }
#[non_exhaustive] pub struct ImageCache;      // new(), with_limits(), ensure(), teardown_bytes()
#[non_exhaustive] pub enum FallbackReason { NotOptedIn, Unsupported, Multiplexer, Remote,
    NotTrueColor }
#[non_exhaustive] pub enum PixelRoute { Pixels, Fallback(FallbackReason) }
pub fn pixel_route(cap: Capability, depth: ColorDepth, force: bool,
                   get_env: impl Fn(&str) -> Option<String>) -> PixelRoute;
```

GREEN adds, outside this slice:
- **A source-preserving pixel image element.** It takes and keeps an `Arc<RgbaRaster>`, the
  same shape as `stage::RasterPlane.source`. Alpha and the source resolution survive lowering,
  next to whatever fitted samples the cell path needs. The element carries no route: no
  `PixelRoute` field on the element or on `ImageOptions`, and no `ImageCache` handle.
- **The kitty-vs-cell decision is a terminal-adapter step on the lowered frame.** The adapter
  calls `pixel_route` and `ImageCache::ensure` per image box, then paints either the placeholder
  cells or the cell-encoder surface into the box. The semantic tree stays backend-neutral, so a
  native backend consumes the same element and the same source raster (release-owner ruling,
  2026-11-20, from the Gibson World GW1 compatibility check).
- A renderer hook that drains a pending-graphics queue ahead of the frame bytes inside the same
  transaction; the teardown and panic wiring of section 8; `delete_all_images()`.

The pieces are exposed as bytes and `Surface`s deliberately: the application can already compose
them by hand (write the upload, paint `placeholder_cells` into a `Surface`, wrap it with
`Node::raster`) before the element exists.

## 13. Integration with the parallel work (own stubs; no dependency)

- **`CellEncoder`** (merged in #436, `docs/design/v0.9-cell-encoders.md`). The fallback
  is that branch's `RgbRaster::to_surface_with(encoder)` / `ui::image_with`. This slice uses no
  code from it: `PixelRoute::Fallback(..)` only says "use the encoder". Its footprint rule (the
  box is fixed by the half-block fit and does not depend on the encoder) is exactly the "same box"
  contract here. Its note that Kitty pixels are "a later slice, behind capability negotiation,
  opt-in" is this document. Both branches add one `pub mod` line to `src/lib.rs` near `glyph`, so
  expect a trivial merge conflict there.
- **Probe verdict** (parallel slice adding a tri-state `kitty_graphics` verdict).
  `pixel_route` takes today's `capability::Capability` (`Supported`, `Unsupported`, `Unknown`),
  which is a tri-state already. The probe's verdict maps one-to-one: a positive reply is
  `Supported`, a negative reply `Unsupported`, no reply or no probe `Unknown`. `Unknown` stays
  fallback; only the application sets `Supported`, or a probe it explicitly ran. The probe must not
  run by default (it races the application's stdin).
- **Alpha.** The avatar is an RGBA sprite. The pixel route sends straight alpha and lets the
  terminal composite it over the cell background (unverified item 4). The encoder path composites
  alpha over a background before encoding; the two routes may differ at soft edges, and that is
  disclosed, not hidden.

## 14. Test plan

`tests/kitty_graphics.rs`. `red_*` fail against the stubs and are GREEN's specification; `guard_*`

## 16. Open questions (owner)

1. **Diacritic table provenance (resolved by release-owner ruling: clean-room).** kitty is
   GPL-3.0 and libgibson is MIT OR Apache-2.0, so no kitty source or data file is copied. The
   table is a generated artifact: `scripts/gen_kitty_diacritics.py` derives it from Unicode 6.0.0
   `UnicodeData.txt` (unicode.org; sha256
   `90b45b777346bef027556f9c6cb3ea5d7d745bd60d6762855c08d8a22d34f771`, pinned and checked by the
   script) by the selection rule the protocol documentation states in words: category Mn,
   combining class 230, bidi NSM, no decomposition mapping, minus U+0300-0304, U+0306-030C,
   U+030F, U+0311, U+0313, U+0314, U+0342, U+0653 and U+0654. The output,
   `src/graphics/kitty_diacritics.rs`, has 297 entries, from U+0305 to U+1D244. On 2026-11-20 it
   was compared once against the published list, and the two match in every entry. That comparison
   was a check only: the published file is not in the repository. The tests pin the count, both
   endpoints and the first 24 entries, all sourced from the rule and the UCD.
2. **One box size per id.** Without the underline-colour placement id, an image has one active box
   size. Is that acceptable, or should `Style` gain an underline colour in a later breaking release?
3. **Id namespace.** Add an application-supplied salt/base to the id so two libraries in one
   terminal do not collide? Default stays the pure content hash.
4. **Resident-image cap and eviction.** Default 16, least recently shown; is it right for a
   several-pose avatar plus a few diagrams? Should eviction use `d=i` first (keep data, let the
   terminal's quota decide) and `d=I` only at teardown?
5. **Frame deferral API.** `ensure` has no notion of a frame; the deferral budget needs a
   `begin_frame` / plan type. Where does it live (`Renderer`, `Context`, a standalone planner)?
6. **`q=2` behaviour and alpha mode** need the real-kitty gate before the first release uses them.
7. **zlib.** Add `o=z` once a compressor is available without a new dependency, or never?
8. **Cell aspect.** The pixel route letterboxes to the box's aspect (verified: aspect preserved).
   Does the element take the cell pixel size from the application, or accept letterboxing?
9. **Support list.** Which terminals besides kitty may an application mark `Supported`? The page
   does not say; this needs a measured matrix, not a guess.
10. **tmux/screen passthrough** as a later opt-in framing, or never.
11. **`Style` underline colour** (see 2) versus a `Cell`-level image attribute: a cleaner model of
    "this cell is an image cell" would avoid pushing meaning through foreground colour, but it
    changes the `Cell` struct.

## 17. Claims and boundaries

- Demonstrated by the tests today (on the existing pipeline, with hand-built cells): occlusion,
  restore, clipping and the idle zero-byte frame need no change to the diff or the renderer.
- Designed, not demonstrated: every byte-level behaviour above (RED), and everything that needs a
  real terminal.
- Not claimed: that any terminal draws the image, that `q=2` is silent, that tmux works, that a
  committed row stays pretty after a terminal reflow, and anything about performance.
