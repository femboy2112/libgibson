# v0.9.1 multi-line text area (design, RED slice)

Status: **RED slice**. The stubs (`src/input/text_area.rs`, the one-label lowering in
`src/ui/compile.rs`) and the failing `tests/text_area.rs` come first; the implementation is the next
slice. Everything is **additive and EXPERIMENTAL** (Rust only, outside the C ABI and bindings).
Nothing here changes `TextInputState`: it stays single-line by contract (issue #252), `single_line()`
still flattens a pasted line break to a space, and `tests/text_area.rs` carries guards for that. The
slice was written without compiling (shared build lock); hosted CI is the first compile.

## 1. API

```rust
// src/input/text_area.rs (private file module of `input`), re-exported as
// gibson::TextAreaState and gibson::input::{TextAreaState, VisualRow}. No new public module.
#[derive(Debug, Clone, Default)]
pub struct TextAreaState {
    pub text: String,
    pub cursor_grapheme: usize,
    pub scroll_row: usize,          // first visible VISUAL row, not a logical line
    pub goal_col: Option<usize>,    // column (cells) Up/Down/PageUp/PageDown return to
}
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct VisualRow { pub start: usize, pub end: usize, pub width: usize }

impl TextAreaState {
    pub fn new() -> Self;
    pub fn with_text(text: impl Into<String>) -> Self;       // sanitized as a paste, cursor at end
    pub fn grapheme_count(&self) -> usize;
    pub fn normalize_paste(s: &str) -> String;                // section 4
    pub fn insert_str(&mut self, s: &str);                    // sanitized, cursor after it
    pub fn handle_event(&mut self, event: &Event, width: u16, rows: u16) -> bool;
    pub fn visual_rows(&self, width: u16) -> Vec<VisualRow>;  // THE wrap function (section 3)
    pub fn cursor_rc(&self, width: u16) -> (usize, usize);    // visual (row, column in cells)
    pub fn update_scroll(&mut self, width: u16, rows: u16);
}

// ui/element.rs (re-exported by ui::prelude through `element::*`)
pub fn text_area<A>(state: &TextAreaState) -> Element<A>;
impl<A> Element<A> {
    pub fn rows(self, rows: u16) -> Self;                     // visible rows, >= 1, default 4
    pub fn on_area_edit(self, f: impl Fn(TextAreaState) -> A + 'static) -> Self;
}
// ui/interaction.rs: Interaction gains `area: Option<(TextAreaState, u16 cols, u16 rows)>` and
// `on_area_edit: Option<Arc<dyn Fn(TextAreaState) -> A>>`.
```

Decisions where the accepted API met the code:

- **`handle_event` takes `rows` as well as `width`.** PageUp/PageDown move by the visible rows and
  `handle_event` is the only place that sees the key. `rows` is only the page stride.
- **`on_area_edit`, not an overload of `on_edit`.** `Element::on_edit` and `Interaction::on_edit` are
  typed `Fn(TextInputState) -> A`; Rust cannot overload, and widening them would break callers. The
  smallest additive parallel is a second callback plus a second snapshot field. The runtime applies
  `handle_event` and then `update_scroll` to a clone and emits the clone, exactly like `on_edit`.
  `Interaction` is a public struct with public fields, so adding two fields is a source break for
  anyone building one by literal; the `ui` module is experimental and only `compile.rs` builds it.
  `stage::map_actions` maps `on_area_edit` like `on_edit`.
- **The wrap width is the element's `.width(n)`** (default 80 cells), used by both editing and
  painting and not clamped by the parent. The runtime does not know a laid-out width, so a
  layout-driven width could make the edit-time wrap differ from the paint-time wrap; fixing the
  width on the element makes disagreement impossible. A parent narrower than `n` clips (as
  `ui::image` does). `.rows(n)` is the visible height; do not also set `.height(..)`.
- **Position: `src/input/text_area.rs`**, a private child of `input`, not a public module, so
  `doc_release_contract_tiers` has nothing new to list. Only `lib.rs` (root re-export) and two lines
  in `input.rs` (`mod text_area; pub use ...`) change; `TextInputState` code is untouched.

## 2. Semantics

All positions are grapheme indices into `text`; cell widths are the editor width contract of
`TextInputState` (issue #252): `editor_cells` / `editor_cell_width` (1- and 2-wide graphemes verbatim,
wider ones codepoint by codepoint, controls / lone zero-width / unplaceable as one `U+FFFD` cell),
with one exception: a **TAB** is one grapheme of fixed width **4** (no tab stops) for wrap, cursor and
painter alike, painted as 4 blank cells (GOD #137 ruling i).

| Event | Effect | Returns |
|---|---|---|
| `Char(c)` (no Ctrl/Alt) | insert (sanitized) | true if the buffer changed |
| `Enter` (plain or Shift) | insert `"\n"` | true |
| `Enter` with Ctrl or Alt | nothing: the application's | false |
| `Backspace` / `Delete` | remove the grapheme cluster before / at the cursor | true if changed |
| `Left` / `Right` | move one grapheme (crosses `"\n"`); clears `goal_col` | true if moved |
| `Up` / `Down` | move one visual row, column from `goal_col` (set on first use) clamped to the row | true if moved |
| `PageUp` / `PageDown` | as Up/Down repeated `rows` times (clamped at the first/last row) | true if moved |
| `Home` / `End`, `Ctrl+A` / `Ctrl+E` | start / end of the visual row (section 3); clears `goal_col` | true |
| `Paste(s)` | insert `normalize_paste(s)` | true if the buffer changed |
| anything else (Tab, Esc, Ctrl+U/K/S, mouse, resize) | nothing | false |

Any edit or horizontal move clears `goal_col`. `handle_event` never scrolls and never normalizes
`scroll_row`; callers (and the runtime path) call `update_scroll` after.

`cursor_rc(width)`: the cursor is on the **last** visual row whose `start <= cursor_grapheme`; its
column is the summed cell width of that row's graphemes before the cursor. A soft-wrap boundary
therefore belongs to the **next** row; before a hard `"\n"` is the end of its row.

`update_scroll(width, rows)` keeps `scroll_row <= cursor_row < scroll_row + rows` and moves
**minimally**: up so the cursor row is the first visible row, down so it is the last. `rows == 0`
or `width == 0` is a no-op. A `scroll_row` past the last row is clamped.

`Home`/`End`: Home is the row's `start`. End is the row's `end` for the last row and for a row ended
by a hard `"\n"` (after its last grapheme). On a **soft-wrapped** row `end` is the next row's start
and `cursor_rc` would put the cursor there, so End lands on the row's **last grapheme** (`end - 1`)
instead (open question 3).

## 3. Wrap rule and the single wrap function

`TextAreaState::visual_rows(width)` is the only wrap function. `cursor_rc`, Up/Down/PageUp/PageDown,
Home/End, `update_scroll` **and the painting path** (section 5) call it and nothing else, so wrap,
cursor and paint cannot disagree. It is deliberately **not** `layout::wrap_text`: that function
measures with uncapped `UnicodeWidthStr`, trims trailing spaces and cannot report grapheme ranges,
so it cannot agree cell for cell with the editor width contract.

1. **The last column is the cursor's.** Rows wrap at `limit = max(width, 2) - 1` cells, so the
   insertion point at the end of a full row still has a cell and no row ever needs a phantom
   successor. Painted glyphs therefore never touch column `width - 1`.
2. Split the text at `"\n"` graphemes (a `"\r\n"` cluster also breaks; a lone `\r` is a control and
   paints as `U+FFFD`). Every `"\n"` ends a logical line; a trailing `"\n"` opens an empty last row.
3. Within a logical line, tokens are maximal runs of non-space graphemes **with their trailing
   spaces** (`split_inclusive(' ')`), widths summed with the editor width contract.
4. Greedy: a token goes on the current row if `row_width + token_width <= limit`. Otherwise, if the row
   is non-empty, break before the token. A token still wider than `limit` is then hard-broken **by
   grapheme**: a grapheme that would overflow starts the next row. A row always takes at least one
   grapheme, so a grapheme wider than `limit` (width < 4) overflows alone rather than looping.
5. Trailing spaces stay on the row they follow and count toward its width.
6. Rows partition the buffer: `rows[0].start == 0`; consecutive rows have `next.start == prev.end`
   (soft wrap) or `next.start == prev.end + 1` with a `"\n"` at `prev.end` (hard break); the last row
   ends at the grapheme count. `VisualRow::width` is the cell width of `start..end`.

Hand-computed pins (all in `tests/text_area.rs`): `"aaa bbb ccc"` at width 9 is `(0,8,8) (8,11,3)`;
`"abcdefghij"` at 5 is `(0,4,4) (4,8,4) (8,10,2)`; `"漢字漢字"` at 6 is `(0,2,4) (2,4,4)`;
`"ab\ncd\n"` at 10 is `(0,2,2) (3,5,2) (6,6,0)`.

## 4. Paste sanitization (the field holds a system prompt)

`normalize_paste` is applied by `Event::Paste`, `insert_str` and `with_text`; `Char` goes through the
same filter. After it the buffer contains no `char` below U+0020 except `'\n'`, none in
U+007F..=U+009F, and no ESC. Single pass, left to right:

- `\r\n` and a lone `\r` become `\n`; `\n` is kept. U+2028 / U+2029 become `\n` (they would paint
  as `U+FFFD`).
- `TAB` is **kept verbatim** (GOD #137 ruling i): the field holds a system prompt, and Reset/Save
  must round-trip byte-exact. Every other C0 control, DEL and every C1 control (including U+0085) is
  removed.
- **ESC-introduced sequences are swallowed whole**:
  - `ESC [` (CSI) through its final byte `0x40..=0x7E`, after parameter bytes `0x30..=0x3F` and
    intermediates `0x20..=0x2F`. A byte outside those ranges (a newline, a non-ASCII char) ends the
    sequence there and is processed normally.
  - `ESC ]` (OSC) up to BEL or ST (`ESC \` or U+009C); `ESC P` (DCS), `ESC X` (SOS), `ESC ^` (PM) and
    `ESC _` (APC) up to ST. An unterminated string sequence swallows the rest of the paste.
  - any other `ESC` plus its intermediates (`0x20..=0x2F`) and one final byte (`0x30..=0x7E`) is
    removed; an `ESC` at the end or before a non-ASCII char is removed alone.
- **C1 introducers behave like their ESC forms**: U+009B (CSI), U+009D (OSC), U+0090 (DCS), U+0098,
  U+009E, U+009F, with U+009C as ST. Terminals that decode UTF-8 treat them as the 8-bit controls.

Hostile example: `"a\x1b[31mb\x1b]0;title\x07c\r\nd\u{9b}2Je\0"` becomes `"abc\nde"`.

Out of scope here: bidi overrides (U+202A..U+202E, U+2066..U+2069), zero-width and tag characters,
which are not control characters and are painted as the editor contract paints them (open question 5).

## 5. Painting and the `text_area` element

Painting and editing share `visual_rows(cols)` with `cols = area_cols(el)`. The GREEN lowering is a
`Node::canvas(..)` sized `cols x rows` (no new `NodeKind`, no change to `layout.rs` / `painter.rs`):
the paint callback receives the node rect, builds a transparent `Surface`, takes
`state.visual_rows(cols)`, and for visual rows `scroll_row .. scroll_row + rows` places each
grapheme with `editor_cells` at the running column (same placement as `paint_text_input`). When
focused it paints the cursor cell at `cursor_rc` with `style.overlay(skin.selection)`: over the
glyph there, or a styled space at the end of a row. An unfocused area paints no cursor. The canvas
callback cannot set the hardware cursor (open question 1), so the software cursor is the only mark.
Canvas content does not affect layout, so `.width(cols)` and `.height(rows)` size it explicitly.

Focus and events: the area is a focusable editor even without a callback. In the runtime it owns
Enter and Space as text (it never activates `on_press`, so a Save placed on the same element cannot
fire from the keyboard), owns Backspace/Delete/arrows/Home/End/PageUp/PageDown, Ctrl+A/Ctrl+E and
paste, and consumes them even when they change nothing. It does **not** own Esc, Ctrl/Alt+Enter,
Ctrl+U/K or any other chord, which stay routable to the application (`outcome.consumed == false`).
Tab and Shift+Tab traverse focus as everywhere (a literal Tab is typed by pasting).

## 6. Commit contract

**The widget never emits a commit.** `TextAreaState` has no commit/submitted flag (a test
destructures its fields exhaustively to keep it so), `text_area` has no `on_submit`, and Enter is
text. The only signal is `on_area_edit`, carrying the edited state.

- The consumer provides an explicit **Save** control (a `button(..).on_press(..)` row next to the
  area) and treats the area's text as a draft.
- **Never rely on Ctrl+Enter.** On a plain VTE terminal it is byte-identical to Enter, so it cannot be
  told apart without kitty keyboard reporting. The area deliberately leaves Ctrl/Alt+Enter unhandled
  and unconsumed so an application *may* bind them as an optional accelerator where the terminal
  reports them; the Save row is the only portable commit.
- **Esc / cancel-restore is the consumer's job**: keep the original value, and on Esc or a Cancel
  button put it back. Esc is not consumed by the area.
- Undo via `edit::EditSession` is optional and out of this slice.

## 8. Open questions

1. **Hardware cursor.** A canvas cannot request it. A dedicated `NodeKind::TextArea` (non-exhaustive,
   additive) would set `ctx.cursor_position` like `TextInput`, at the cost of arms in `painter.rs`,
   `layout.rs` and hit/skin code. Software cursor for the slice?
2. **Layout-driven width.** A fixed `.width(n)` avoids edit/paint disagreement but cannot flex.
   Flexing needs the laid-out width fed back to the application (a `PaintContext` field or a resize
   callback). Defer?
3. **End on a soft-wrapped row** lands on the last grapheme because the state has no row affinity. An
   `affinity` field (or a "cursor after last grapheme" flag) would allow true end-of-row; it widens the
   accepted state.
4. **Reserved cursor column** (wrap at `width - 1`): RULED OK (GOD #137 iii). Why: the cursor sits
   *after* the last grapheme of a row, so a row filled to `width` would leave the end-of-line cursor
   no cell. It would have to be drawn at column 0 of a phantom next row, which disagrees with
   `cursor_rc` and scrolling. Reserving the last column costs one column everywhere and removes that
   case.
5. **Bidi / zero-width / tag characters** are not stripped (only controls are). For a system-prompt
   field, strip U+202A..U+202E and U+2066..U+2069 too?
6. **TAB**: RULED (GOD #137 i). It is kept as `\t` (neither converted nor stripped), as one grapheme
   4 cells wide. The no-control invariant excludes `\n` and `\t`. U+2028/U+2029 becoming `\n` is
   RULED OK (iv). **C1 sequence swallowing** (U+009B `2J` removed whole)
   is stricter than dropping the single control char; the single-char rule would leave `"2J"` text.
7. **Ctrl+U / Ctrl+K** (kill line) are unsupported, not aliased to the input's line-kill; add as
   logical-line kills if wanted.
8. **`Interaction` gaining public fields** is a source break for external literal builders: RULED OK
   for the EXPERIMENTAL `ui` module, with a CHANGELOG note (GOD #137 ii). (The alternative was a non-exhaustive `Interaction` first.)
