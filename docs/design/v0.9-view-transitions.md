# v0.9 view transitions: `SurfaceFx::Offset` and `SurfaceFx::Blend`

Status: RED slice. The variants exist and `apply` is a no-op stub; the tests in
`tests/surface_fx_transitions.rs` define the contract and fail until it is implemented.
Goal: continuous view transitions, "desktop-app feel, no jolts or flash".

## Signatures

```rust
pub enum SurfaceFx {
    // ... existing variants ...
    /// Shift the whole entity-local surface by (dx, dy) cells.
    Offset { dx: i32, dy: i32 },
    /// Move fg and bg of every painted cell toward `toward` by `t`.
    Blend { toward: Color, t: f32 },
}
```

Both are fully realized values like the other variants: no clock, no hidden state.

## Offset semantics

- The whole entity-local surface moves by `(dx, dy)`; positive is right/down.
- Cells moved outside the surface are clipped. Vacated cells become transparent (like
  `RowShift`), exposing the layer beneath.
- A wide glyph is moved or clipped as a whole. If its lead and continuation do not both land
  inside the surface it is dropped; no orphan continuation may appear on the edge.
- Style-only cells move like narrow cells. Transparent cells stay transparent.
- `Offset { dx: 0, dy: 0 }` is exact identity. Chains stay ordered, never commuting by
  assumption (`Offset` then `Blend` equals `Blend` then `Offset` only because Blend is
  position-independent).
- Suggested implementation: a scratch `Surface::new_transparent` plus
  `blit_transparent_clipped` already clips wide glyphs whole. Caveat: blit overlays
  style-only cells onto the (transparent) destination instead of copying them, so copy
  cells directly for those. `shift_row` is the pattern for the per-row case.

## Blend semantics

- Applies to every painted (non-transparent) cell, including style-only cells and wide
  continuations (which share the lead's style). Transparent cells are untouched.
- `t` is clamped to [0, 1]; NaN is treated as 0. `t = 0` is identity, `t = 1` sets fg and bg
  exactly to `toward`.
- Per channel (fg and bg independently) with both endpoints resolvable (`Rgb`, `AnsiN`, or a
  named colour): `Color::lerp_resolved(toward, t)`, giving `Rgb` with per-channel rounding.
  Note `lerp_resolved` itself does not guard NaN; `Blend` must clamp first.
- Glyphs and attributes (bold, dim, italic, underline, reverse) are unchanged.

### Reset / unresolvable endpoint rule (proposed)

`Color::Reset` means "terminal default" and has no RGB value. `Color::lerp` would invent
`(204, 204, 204)`. Proposed rule: when the cell channel is `Reset` or unset (`None`), or
`toward` is `Reset`, use a step: keep the original for `t < 0.5`, take `toward` for
`t >= 0.5`. No fake gray is ever produced. The step is a visible pop for default-coloured
cells; an app that wants a smooth fade must give its cells explicit colours (this is the
documented consequence, and the tests pin it).

Unset (`None`) channels follow the same step rule, so a fade-out toward the background
colour does hide default-coloured cells at `t >= 0.5`. Open: whether `None` should instead
be left alone.

### 256-colour and 16-colour behaviour

`Blend` always writes `Rgb`; downsampling is the renderer's job (`capability::quantize_color`,
`nearest256`). Along the grey axis (black toward white) nearest-palette selection is monotone,
so an 8-step sweep never moves away from the target, and `t = 1` lands exactly on the target
palette entry; the tests assert this. For arbitrary hues the xterm cube is non-uniform and
monotonicity of the quantized path is not guaranteed; the tests only assert it for the
unquantized path and exact arrival at `t = 1`. At `Ansi16` and `Mono` a fade is necessarily
coarse (16 steps of colour, or none). Apps should drive such fades with `Dim`/`Dissolve`
or snap. Open: ordered dithering across the sweep to hide palette stepping.

## How an app does a slide or a cross-fade

Exit ghosts (keeping a removed view alive for its exit animation) are deferred, so the app
keeps the outgoing view itself and drives a 30 fps `Tick`:

1. On navigation, keep `outgoing` (its element/node) alongside `incoming`; record `start`.
2. Each `Tick`, compute `p = ease(elapsed / duration)` in [0, 1].
3. Slide: wrap both views as nodes; `outgoing.post_process([Offset { dx: -round(p*W), dy: 0 }])`
   and `incoming.post_process([Offset { dx: round((1-p)*W), dy: 0 }])`, stacked in one
   parent. The vacated cells are transparent, so no blank flash between them.
4. Cross-fade: stack both; `outgoing` with `Blend { toward: bg, t: p }`, `incoming` with
   `Blend { toward: bg, t: 1 - p }`, so the seam passes through the surface colour (no true
   alpha exists; see `surface_fx.rs` module docs).
5. At `p = 1` drop `outgoing` and clear the fx: the settled tree is the plain incoming view,
   byte-identical to a view that was never animated.

Wiring today: `Node::post_process` (applied in `src/painter.rs` on the node's local surface).
The ui `.motion` / `MotionPlan` path (`src/ui/motion.rs`) only emits fixed role grammars
and cannot carry `Offset`/`Blend` yet; an element-level `post_process` for these fx is the
open ask. Differential rendering already writes only changed cells: a slide of a mostly
static backdrop costs the moving content plus the vacated edge, never a full clear.

## Sprite-present testing rule (owner rule)

Every transition test must also run with a truecolor sprite region on the surface. The test
fixture is synthetic: a 12x6 block of `\u{2580}` half blocks, distinct `Rgb` fg and bg per
cell from a deterministic formula defined in the test file. No avatar or image asset is used
or read. `Offset` must move the sprite intact (glyph, fg, bg of every cell preserved at the
shifted position, nothing outside the clip); `Blend` at `t` must apply the exact per-cell
lerp to the sprite's own colours. The renderer test slides a full view containing the sprite
through 8 frames: no frame after the first contains `\x1b[2J` (a fullscreen first frame may
clear to anchor), each later frame writes fewer bytes than the first full paint, and the
presented cells carry the sprite at the shifted position.

## Breaking change

Adding variants to the public `SurfaceFx` enum breaks downstream exhaustive `match`es.
Acceptable for 0.9.0.

- **Release-owner ruling:** `SurfaceFx` gets `#[non_exhaustive]` in 0.9.0, so later variants are
  not breaking. Downstream `match` sites need one wildcard arm.
  The only crate-internal exhaustive match is `SurfaceFx::apply` in `src/surface_fx.rs`.
  `#[non_exhaustive]` does not affect in-crate matches.
- **C ABI and bindings:** `SurfaceFx` does not cross them. It has no occurrence in
  `include/`, `abi/` or `bindings/`, so this change does not touch the ABI version.
- **Consumer pre-check:** Minerva (ProjectGHOST main `4171b3d`, 253 `.rs` files, 60 of
  them using libgibson) has 0 references to `SurfaceFx`, so 0 exhaustive matches. The
  0.9.0 consumer gate will confirm this.
- **Other public enums 0.9.0 may grow:**
  - `ui::ControlRole` (`src/ui/skin.rs`): exhaustive, and custom skins match on it. If
    `toggle` gets its own role, add `#[non_exhaustive]` with it.
  - `Event` and `MouseKind` (`src/input.rs`): already `#[non_exhaustive]`, so pointer
    routing needs no change there.
  - `ElementKind` is `pub(crate)` and does not apply.
  - No blanket change.

## Open questions for NAV-1

1. Should `Offset` support fractional/sub-cell motion (half-block vertical, 2x vertical
   resolution) or stay integer cells? This slice assumes integer cells.
2. Where do transitions live: element-level `post_process` on the ui layer, a `MotionPlan`
   role (`Navigate`?), or app-only? Who owns the outgoing view's lifetime once exit ghosts
   land?
3. Reset/`None` step rule: accept, or require explicit colours, or resolve against the
   skin's background at lowering time?
4. Easing and duration live in the app. Provide helpers (ease-in-out, 30 fps clamp) in
   `gibson::ui`, or keep fx values dumb?
5. Reduced-motion: map `Offset`/`Blend` to `MotionPreference::Reduced` as an instant switch
   or a short `Blend` only. Which?
6. `Blend` toward `Reset` (the terminal default): step to `Reset` at `t >= 0.5`; is a
   fade-to-default ever wanted, or should it be rejected?
7. Hit-testing: `src/ui/hit.rs` documents targeting as the pre-effect extent whenever any
   fx applies (disclosed, not exact). During a slide pointer targets lag the pixels;
   acceptable, or freeze input while a transition runs?
8. Should `Blend` also cover cells whose colour comes from the terminal's underlying
   layer (transparent cells)? This slice says no: transparent stays transparent.
