## Question

Is 0.6.0 released, and if so from which commit? The qualified candidate is on
`release/v0.6.0-rc`, but Release Contract §1 (state 2) says a `v<version>` tag "names a `main`
commit".

## Context (verified 2026-11-07)

- **Every release so far is on `main`.** All twelve tags `v0.1.0` … `v0.5.0` name commits on
  `main`'s first-parent history. `bindings/go/v0.5.0` → `d8c7b99` is the only Go module tag.
  v0.5.0 is a GitHub prerelease with four assets: `libgibson-0.5.0-linux-x86_64.tar.gz`, its
  `.sha256`, `libgibson-0.5.0-py3-none-any.whl` and `libgibson-0.5.0-python-sdist.tar.gz`.
- **The 0.6.0 source commit is held.** `9a899e1` (merge of #261) prepared 0.6.0 in source on
  `main`'s first-parent history: C ABI v1 with 59 symbols, MSRV 1.85. It carries #264 (an idle
  `run_once` busy-spins) and #269 (a terminal hangup during a poll spins forever), so it was not
  tagged.
- **`main` has moved on.** `main` (`5790f1a`) is `0.7.0-dev`, 97 commits after `9a899e1`, with 62
  symbols (`gibson_push_event`, `gibson_push_event_kind` and `gibson_poll_event_kind` added).
- **A qualified candidate exists off `main`.** `release/v0.6.0-rc` @ `1b90b48` is `9a899e1` plus
  ten commits: three for #264, five for #269/#15, an RC-only test adaptation and a CHANGELOG entry
  ([`V06_QUALIFICATION_LEDGER.md`](../V06_QUALIFICATION_LEDGER.md), Renaissance XVIII). CI run
  42335104064 and Release Preflight run 42335106128 both succeeded on exactly `1b90b48`.
  `check-maintenance-candidate.sh --baseline 9a899e1 --candidate 1b90b48` passes, and a library
  built from `1b90b48` exports exactly the 59 baseline symbols.
- **The candidate is not final.** An independent audit on #287 (2026-11-07) adds a HOLD
  criterion: the candidate still has #259, so a headless context reads the real terminal. That
  contradicts the 0.6 contract's "output-only" headless C ABI. PR #288 (open, base
  `release/v0.6.0-rc`, head `c4233ba` when this was written) backports the fix, and the audit asks
  for #285 to be evaluated. At `c4233ba` every content check passes (ancestry, version, ABI,
  headers, MSRV, PCM golden). Only the branch check fails, because the commit is not yet on
  `release/v0.6.0-rc`.
- **The branch is not protected on GitHub** (the API reports "Branch not protected"). The proposed
  policy relies on exact-SHA qualification instead.
- **The candidate's own contract is unamended.** The `docs/RELEASE_CONTRACT.md` inside the
  candidate tree still has the unamended §1.
- **A pushed tag cannot be taken back.** The repository is public. Once a Go module tag is pushed,
  the Go module proxy can serve it and the Go checksum database records it permanently. This is
  how the Go ecosystem works; it was not measured here.

## Options

### A. Release 0.6.0 from the maintenance branch under the proposed policy (recommended)

The owner adopts the maintenance-line exception. In a separate approval for this release, the owner
then authorizes `v0.6.0` and `bindings/go/v0.6.0` on one qualified SHA of `release/v0.6.0-rc`.

- **Users gain** an installable 0.6.0 now. It carries the v0.6 surface (the 59-symbol C ABI with
  headless contexts, output and cell-grid readback and colour-depth selection; the live wire
  instrument; renderer recovery from partial writes) plus the #264 and #269/#15 fixes, and #259
  once #288 lands.
- **It costs** a second line to qualify and record. The tag is not reachable from `main` unless
  the branch is merged back. 0.6.0's tree is not `9a899e1`, so text that says a v0.6.0 tag names
  `9a899e1` must be corrected. The disclosed limitations ship: #274, #285 unless it is fixed, and
  crossterm input off Unix.
- **Why recommended:** it ships qualified fixes under the version users were told to expect. It
  does not downgrade `main` or import 0.7 API; the checker enforces the ABI, header, MSRV and
  golden freeze. It leaves an auditable trail: baseline ancestry, an allow-listed commit range and
  an exact-SHA approval.

### B. Retire 0.6.0 unreleased

0.6.0 stays "prepared in source, never released". Its content and the RC's fixes ship only in
0.7.0, from `main`.

- **Users lose** any release of the v0.6 surface or of these fixes until 0.7.0, which has no date
  ([`V07_EXECUTION_GRAPH.md`](../V07_EXECUTION_GRAPH.md): "PLAN, in execution"). Users of 0.5.0
  keep its known defects in the meantime, including the #15 resize/key stall (Release Contract
  §9: "Released versions up to 0.5.0 … still have the stall"). This record does not establish
  whether #264 and #269 also affect 0.5.0.
- **Users gain** one release line. Nothing released carries #259's headless-input contradiction.
  0.7.0 arrives with #259 fixed and with `gibson_poll_event_kind` / `gibson_push_event_kind` (#274).
  A C consumer goes from 52 symbols (0.5.0) to 62 in one additive step; `GIBSON_ABI_VERSION`
  stays 1.
- **Maintainers gain** no amendment, no maintenance branch and no back-merge.
- **Version gap 0.5.0 → 0.7.0.** 0.x SemVer allows it (a `0.y` minor is the breaking slot, so a
  `libgibson = "0.5"` requirement never resolves to 0.6 or 0.7 anyway). The string `0.6.0` remains
  in history at `9a899e1` and on `release/v0.6.0-rc`. A git dependency pinned there builds a crate
  that calls itself 0.6.0 but was never released.
- **Go.** Module versions go from `bindings/go/v0.5.0` to `bindings/go/v0.7.0`. Go accepts the gap.
  `v0.6.0` and `bindings/go/v0.6.0` must never be pushed afterwards, because the checksum
  database would record whatever they first served. Python never distributes 0.6.0.
- **Edits it implies** (a docs PR on `main`):
  - CHANGELOG: the `## [0.6.0] — prepared in source … not tagged, not released` heading becomes
    "never released (retired)", and the `[Unreleased]` line "a future `v0.6.0` tag names that
    commit" goes.
  - Release Contract: the §1 0.6.0 milestone entry, and the scope of §9's "v0.6 Engineering Alpha
    limitations".
  - README (the "v0.6.0 is prepared in source at `9a899e1`" banner and "until a v0.6.0 release
    exists").
  - ROADMAP (current direction, state legend, the 59-symbol and headless-limit notes),
    `docs/STATE_OF_LIBGIBSON.md` and the Renaissance XVIII verdict in `V06_QUALIFICATION_LEDGER.md`.
  - The fate of `release/v0.6.0-rc`: keep it unmodified as the record of a qualified, unreleased
    candidate, or delete it. That is the owner's call.

### C. Tag `9a899e1` as is (rejected)

This is the only option the current §1 permits without an amendment, because `9a899e1` is a
`main` commit. It is rejected on content:

- It ships #264 and #269, which the RC exists to fix, and also #259.
- The round's brief already rejected it (#287).
- A pushed tag is effectively permanent (see Context), so this would publish a known-defective
  v0.6.0 for good.

## Requirements on the candidate (option A)

- **Branch** `release/v0.6.0-rc`. **Baseline** `9a899e1d35025894725c5b14aa8836349fc01825`.
- **Candidate:** one full SHA on that branch, frozen after #288 is resolved and #285 is evaluated
  ([`RELEASING.md`](../RELEASING.md) §7 steps 2–3). `1b90b48` is qualified only for
  #264/#269/#15. Under the audit's HOLD criterion it is not the final candidate.
- **Checker** `RESULT: PASS` at that SHA with `--allow-commits-file`, which lists every commit
  after `9a899e1` as `backport` (citing its `main` counterpart: #281 `1a9c0f5`, #282 `04c0ad2`,
  #265 `a172723` for #259) or `release-engineering`.
- **CI and preflight:** full CI (every job) and the publication-free Release Preflight at that
  exact SHA. The hangup PTY tests pass on their first attempt, and both MSRV floors pass. #259's
  headless, no-TTY and real-PTY C-ABI tests are included, and an independent review covers every
  backport.
- **Artifacts** are built from the tagged tree. `--so` confirms the 59 exports. Four assets go up,
  their checksums are verified after download, and `bindings/go/v0.6.0` names the same commit.
- **Sub-decision 1 (the candidate's own contract):** either backport the approved §1 amendment
  onto `release/v0.6.0-rc` as a `release-engineering` commit, so the tagged tree states the rule
  it was released under, or accept that `main`'s contract governs. Bundled with #288 before the
  final freeze, the backport costs no extra qualification round.
- **Sub-decision 2 (back-merge):** merge the branch back into `main` or not. That merge has its
  own acceptance (`RELEASING.md` §7 step 13) and is never implied by the release.

## What an approval must state

The policy and the release are approved separately; one may be given without the other.

1. **Policy:** "I approve the maintenance-line exception to Release Contract §1 as proposed in
   PR #⟨n⟩." (Its text then loses the *Proposed* marking.)
2. **Release:** "I authorize tagging `v0.6.0` and `bindings/go/v0.6.0` at ⟨40-hex SHA⟩ on
   `release/v0.6.0-rc`, baseline `9a899e1d35025894725c5b14aa8836349fc01825`, under that
   exception, and publishing a GitHub prerelease whose four assets are built from that commit."
   The release approval also states sub-decisions 1 and 2. A new commit on the branch voids it.

For option B, the approval states that 0.6.0 is retired unreleased and that `v0.6.0` /
`bindings/go/v0.6.0` will not be created.

## Decision

**PENDING (owner).** This record proposes and does not decide. When the owner decides, record
here the option chosen, the exact wording and date of the approval, and, for option A, the tagged
SHA, the qualification record and the release URL. If the owner approves the policy, a CHANGELOG
`[Unreleased]` "Release engineering" entry records it in the same change; #257's contract change set
that precedent.
